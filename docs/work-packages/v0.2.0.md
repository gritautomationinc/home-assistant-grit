# GRIT Hub HA integration v0.2.0: safe state authority, hardening, and Hub v1.1.1197 parity (Wave 1 plus Wave 2)

This document is the approved implementation work package for release `v0.2.0` of the Home Assistant custom integration domain `grit_hub`.

Private references have been scrubbed. Any mention of the owner's live Home Assistant, home network, or personal setup details is intentionally generic. No credentials, tokens, passwords, private IPs, or diagnostic payloads are included.

## Objective

Ship integration release `v0.2.0`. In this release Home Assistant reports a GRIT lock, gate or switch as "confirmed" only on device-originated evidence. GRITLock stays visible and commandable across Hub restarts. No service parameter can reach a Hub route other than the one intended. `device_command` executes commands. The options flow opens on HA 2026.11.1. Stale devices can be removed. MQTT logging is quiet for legitimate non-device traffic and specific for real faults. The integration declares and checks the Hub version it was verified against (`GRIT-hub v1.1.1197`). It no longer ships a default MQTT password: new setups require a per-hub read-only credential, and existing entries that still use the vendor default keep working with a repair issue prompting the user to replace it.

### Part A, root-cause diagnosis (read-only)

#### F3: why GRITLock becomes `unavailable`

1. Every MQTT disconnect wipes GRITLock state. `set_mqtt_connected(False)` calls `_reset_gritlock_mqtt_state()`. `lock.py` reports the entity available only while `gritlock_state` is a bool.
2. Re-hydration only listens for trigger `sts` or `tel` carrying `gls`, for 5 s after MQTT readiness. The window opens in `set_mqtt_connected(True)`.
3. The only message HA solicits cannot carry `gls`. Reconciliation calls `POST /api/device/mesh-telemetry/refresh/{type}/{id}`. The Hub turns that into `req-tel`. The device answers on `tel`, whose Hub schema is radio and mesh metrics only, with no `gls`. For triggers, the integration does not wait for the reply.
4. The Hub does not retain the lock topics. `gl` is published with retain false. Only `sts` is in the trigger retainedTopics. The Hub treats `gls` inside `sts` as optional.
5. Live timing observed during a Hub restart: REST recovers, MQTT reconnects quickly, and the 5 s hydration window starts before triggers have rebooted or re-registered. Trigger registration arrives tens of seconds after the window closes, so hydration fails.
6. The answer is already on the Hub's REST surface, unused. The Hub persists per-trigger `gritLockState` and derives system lock state from it. The integration parses `gritLockState` but only uses `gritLockEnabled`.
7. Deadlock: HA drops unavailable entities from entity-service calls. `lock.lock` and `lock.unlock` become no-ops, so no `/gl` burst is produced, and only the GRIT app or Hub can unstick the entity.
8. Why REST 404/502 precede the warning: a Hub restart takes Express (REST) and the on-Hub broker down together. REST recovers first, MQTT reconnects shortly after, and telemetry refresh calls may fail or inventory may be incomplete while the Hub is still starting.
9. Unexplained: an HA-start path exists where reconciliation and hydration ordering differs. Ticket T5 adds a regression test for it.

#### F9: the 60 s "invalid JSON" flood

1. Publisher chain: the Hub publishes a hub announcement every 60 s to `grit/{hub}/hub/a`. The gateway forwards it with `sendWithBSID`, which builds a plain-text frame `SENDWITHBSID ...;`.
2. For the hub announcement target, the frame fans out to every XTNDR on `grit/{hub}/mesh/{xtndrId}/to`. This 5-level topic matches the integration subscription `grit/+/+/+/#`.
3. The integration does not filter it: `mqtt_live.py` runs `json.loads` before topic parsing and validation. The hub id and device-type allowlist are applied later.
4. The wire contract is mixed by design. The Hub itself accepts non-JSON payloads, and the gateway forwards non-JSON device frames verbatim. So the integration warning is a false positive against the wire contract.
5. Collateral: a common workaround is setting the integration logger to ERROR. That hides the false warnings, but also hides real WARNINGs about MQTT connection loss and subscription failures.

#### F10: RFID locks `unknown`, solenoids with no MQTT data

1. Short-topic hypothesis disproved: the Hub subscribes to short paths, but per-type handlers parse only long-form topics. Ignoring short paths loses no lock or switch state in the integration.
2. RFID lock state is REST-only and mirrors Hub memory. The integration reads RFID `state` from REST. The Hub fills `state` only from its in-memory state service, updated when the reader sends `st` or registers with `sts`. So "unknown" means the Hub has not observed that reader's state since the Hub process last started.
3. The MQTT "last received" metric undercounts. The integration updates `last_received_at` only when certain fields are present. RFID `st` schedules a REST refresh but does not update `last_received_at`, and RFID registration `sts` does not schedule a refresh. Devices that publish only on change or registration can show `unavailable` for last-received after a reconnect.
4. Net fix scope for Wave 2: refresh RFID REST on `sts`, record `last_received` for every accepted device message, expose "never seen this session" distinctly, and document that RFID lock state is the Hub's in-memory observation.

## Constraints

- Wire formats: Hub v1.1.1197 contract
  - Compact keys, with booleans as 0/1 on the mesh wire.
  - Device-originated GRITLock completion is `gl-d`. The Hub to trigger command is `gl`. In `gl` payloads, `gte` = gateTriggerEnabled, `gle` = gritLockEnabled, `gls` = gritLockState.
  - Gate: command `mv`, completion `mv-d`, status `sts`.
  - Solenoid: command `s`, report `st`, status `sts`.
  - Non-JSON payloads are legal on `grit/{hub}/mesh/*` and must be ignored silently.
- Hub REST
  - Execute command = `POST /api/command/...`.
  - Lockout = `PUT /api/hub/lockout` with boolean `state`. 502 = partial, 409 = superseded.
  - Health = `/health-check`.
  - API tokens cannot use `requireHumanAdmin` routes.
- HA compatibility: must load and pass on HA Core 2026.11.1 and keep `hacs.json` minimum 2026.3.0 unless T1 proves newer is required. No writes to `OptionsFlow.config_entry`.
- Backward compatibility
  - All existing `unique_id`s are unchanged. Registered `entity_id`s are unchanged. Only friendly names change with F14.
  - The removed buttons' registry entries are removed by the integration on setup, not orphaned.
  - Config entry schema stays version 1 unless options require a migration.
  - Services keep their names; `device_command` gains strict schemas, so an invalid call fails loudly instead of being misrouted.
- Safety
  - A lock, gate or switch confirmation only on a device-originated topic.
  - Fail closed: unknown state is shown as unknown, never as the commanded state.
  - No automated test publishes to a broker or calls a live Hub.
  - No representation as a safety system.
- Secrets
  - Tokens never in logs, exceptions, diagnostics or fixtures.
  - Logged MQTT topics are sanitised (hub id and device id are allowed; payload text is never logged).
  - No private IPs in docs or fixtures.
  - The integration must not ship a default MQTT password.
- Bounds
  - Keep the existing caps (`MAX_MQTT_PAYLOAD_SIZE`, topic limits, `_MAX_MQTT_STATE_WAITERS`, `_MAX_RFID_STATE_TARGETS = 64`, `_MAX_CONFIRM_TIMEOUT = 30 s`).
  - New rate-limited warnings: at most 1 per (reason, device_type) per 10 min.

## Acceptance criteria (AC)

Each item is checkable by a reviewer who did not write the code. "Fixture" means a test input built from the cited Hub v1.1.1197 source.

1. F1, GRITLock authority
   - A `grit/{hub}/trigger/{id}/gl` frame (`gls=1`) does not change `lock.*_gritlock` state and does not satisfy `async_lock` confirmation.
   - A `gl-d` frame from every REST-participating trigger (`gritLockEnabled=true`) does satisfy it.
   - A partial `gl-d` set ends in a `HomeAssistantError` naming the count of unconfirmed triggers.
   - `gte` has no effect on participation; `gle` and REST `gritLockEnabled` do.
2. F2, command echo removal
   - A retained or live gate `mv {p:100}` does not change cover position or open state; `mv-d`, `sts` or `st` do.
   - A solenoid or powerbank `s` frame does not change `switch.is_on`; `st` and `sts` do.
   - A cover or switch confirmation is satisfied only by device-originated topics.
3. F3, GRITLock availability and REST seed
   - After an MQTT reconnect, `lock.*_gritlock` stays available with state `unknown` (not `unavailable`) whenever the Hub REST is reachable.
   - If REST triggers carry `gritLockState` for every participant and they agree, the state is seeded from REST within one poll (30 s or less).
   - Late trigger `sts` or `gl-d` frames arriving after the 5 s window still update the state.
   - The HA-start path is covered by a test.
   - A lock or unlock service call while the state is `unknown` reaches the Hub.
4. F4, device command execute
   - `grit_hub.device_command` issues `POST /api/command/{type}/{id}/{name}/{action}/{remote_type}` with the body shape the Hub expects.
   - No code path issues PUT to `/api/command/`.
5. F5, path hardening
   - For every service and API method that builds a path, any segment equal to `.` or `..`, or containing `/`, `\\`, `%2f`, `%2e%2e`, a control character, or more than 128 characters, raises `ServiceValidationError` before any HTTP call.
   - `device_type` and `remote_type` are enum-validated.
   - A regression test reproduces the traversal tuple and asserts no request is made.
6. F6, options flow
   - On real HA (T1 harness), opening the options flow returns a form, and submitting it updates options without an exception.
7. F11, restart/reboot removal
   - The restart and reboot button entities no longer exist after upgrade, and their registry entries are removed on setup.
   - `api.restart_service` and `api.reboot_hub` are removed.
   - Release notes state the removal and why (Hub requires a human admin session).
8. F7, stale-device removal
   - `async_remove_config_entry_device` lets a user delete a device absent from the last successful, complete Hub inventory, and returns False for devices still present.
   - Optional automatic pruning (option, default off) removes a device only after it has been absent from N 3 or more consecutive complete inventories, never on a failed or partial poll.
   - REST-deleted gates are no longer re-appended by `_preserve_mqtt_state`.
9. F9, MQTT topic gating before parse
   - Topic structure, hub id and device type are validated before `json.loads`.
   - Messages on `grit/{hub}/mesh/#`, `grit/{hub}/hub/#`, `global`, `gateway`, and any device type outside `DEVICE_TYPES` are dropped at DEBUG with no WARNING.
   - Non-JSON on an allowed device topic logs one rate-limited WARNING naming the topic (no payload).
   - Fixture: 1,000 `mesh/{x}/to` `SENDWITHBSID ...;` frames produce 0 WARNING lines.
10. F10 (revised)
   - An RFID `sts` triggers one coalesced REST refresh.
   - Every accepted device message updates `last_received`.
   - Docs state that the RFID lock state is the Hub's in-memory observation, and that "unknown" means the Hub has not seen the reader since it started.
11. F12, lockout semantics
   - A lockout 502 raises an error saying the lock was partially applied.
   - A 409 says superseded by a newer request and does not mark the entity failed.
12. F13, health-check reporting
   - A `/health-check` failure with status 503 is reported as identity unavailable (503).
   - The `GET /` fallback runs only when `/health-check` returns 404.
13. F14, naming
   - New installs produce `lock.bandsaw` (not `lock.bandsaw_bandsaw`). Existing installs keep their registered entity_ids, and only the friendly names change (verified by test on a pre-populated registry).
14. F15, bool_state
   - `bool_state` returns the same result for equivalent dict and string shapes.
   - Precedence is documented and tested against fixtures of the Hub's actual state responses.
   - Unknown shapes return None.
15. F16, version gate, manifest, compatibility docs
   - At setup, the integration reads the Hub `softwareVersion`. Below `1.1.1197` or unparseable, HA repair issue "Hub version not verified with this integration" (non-fatal).
   - `manifest.json`: `version` `0.2.0`, `iot_class` `local_push`, `requirements` `paho-mqtt>=2.1.0,<3`.
   - `docs/COMPATIBILITY.md` lists `0.2.0` to GRIT-hub `v1.1.1197` to HA 2026.11.1.
16. F18, MQTT credential hardening
   - `DEFAULT_MQTT_PASSWORD` is removed from `const.py`. Config flow and options flow do not treat a blank password as the vendor default.
   - A new config entry cannot be created without an explicit MQTT username and password.
   - An existing config entry that was using the vendor default keeps connecting. It raises a non-fatal HA repair issue prompting the user to enter the per-hub credential.
   - Tests cover: new installs reject a missing credential; existing default entries keep working and raise the repair issue; translations do not contain a fill-in default password value.
   - `README.md` tells the user to copy the Hub's per-hub read-only credential (once the Hub change ships, or set by the installer today) and does not document a shared default password.
17. Release
   - All tests pass, with any intentionally changed behavior listed.
   - hassfest and HACS workflows are green (HACS topic warning is a repository setting and is not code-fixable).
   - `CHANGELOG.md` has a 0.2.0 entry mapping each finding to its ticket.

## Design assurance

- [x] Authority. The device is the authority for physical state. The Hub is the authority for inventory, config and its persisted per-trigger `gritLockState`. Home Assistant reports, and never invents.
- [x] Data flow. Traced end to end for GRITLock (HA to `PUT /api/hub/lockout` to Hub to device to `gl-d`), gate (`mv` to `mv-d`), solenoid (`s` to `st`), RFID (REST `state` from Hub memory), and the F9 hub announcement chain.
- [x] Identities. Unique-ids unchanged. Registry entity_ids persist across the name change. The removed buttons are explicitly deleted. Multi-hub collisions are a known Wave 3 risk and are documented.
- [x] Ordering. Paho to event loop FIFO via `call_soon_threadsafe` is preserved. Per-category ordering markers are kept. New rule: a `gl-d` with a generation older than the last HA request is ignored (design input needed: confirm the firmware echoes the generation).
- [x] Bounds. Existing caps are preserved. New warning rate limit is 1 per reason and device_type per 10 min. The prune threshold N 3 or more is bounded by poll count.
- [x] Clocks. Monotonic clocks for windows and timeouts. `last_received` is UTC and Home Assistant renders it local.
- [x] States. GRITLock: `unavailable` (Hub REST unreachable), `unknown` (reachable, no evidence), `locked`, `unlocked`, `jammed` (participants disagree). Illegal: any transition caused by a Hub to device command topic.
- [x] Failure semantics. Fail closed on confirmation: no device evidence means not confirmed. Fail open on availability: Hub reachable means the entity stays commandable.
- [x] Partial failure. Lockout 502 is reported as partial. A partial `gl-d` set reports the unconfirmed count. A partial inventory never prunes.
- [x] Interruption. Home Assistant restart, broker restart and Hub restart are covered by tests, including the HA-start path and the Hub-restart timing regression fixture.
- [x] Retry. The Hub retries lockout commands. Home Assistant never auto-retries lock commands.
- [x] Duplication. Duplicate `gl-d` or `sts` frames are idempotent per trigger id in the observation map. Retained replays are treated as old evidence.
- [x] Stale evidence. Retained command topics are ignored. Retained status topics are accepted as status but marked retained in diagnostics. MQTT state is not wiped on disconnect, it is marked stale. REST `gritLockState` is used as a seed, with source attribution.
- [x] Migration. No breaking config-entry migration expected. Button registry cleanup on setup. Older Hubs get a repair issue. T20 raises a repair issue for entries still using the vendor default MQTT credential, those entries keep working.
- [x] Negative cases. Malformed, non-JSON and foreign-hub topics; traversal; unknown remote_type; oversize; unknown RFID shape. All have tests.
- [x] Observability. Warnings name a reason and topic class. Lock attributes expose the evidence source and the unconfirmed trigger count. Removing any logger workaround becomes safe under production-acceptance.
- [x] Security. Path hardening closes traversal. The removed buttons shrink the surface. Token handling is unchanged. No payloads or IPs in logs. T20 stops shipping a default MQTT password.

## Does this need an ADR

Yes, two, written before implementation:

- ADR 0001: Device-state authority. Only device-originated topics (`gl-d`, `st`, `sts`, `mv-d`, and `tel` for radio metrics only) are observations. Hub to device command topics (`gl`, `s`, `mv`) never are. GRITLock participation comes from `gritLockEnabled` or `gle`, never `gte`. Hub REST `gritLockState` is a labelled seed. This changes the canonical state model and safety invariant, and closes the Home Assistant-side mechanism of issue #33.
- ADR 0002: Hub compatibility contract. The integration pins a verified Hub version (`1.1.1197`). It warns via a repair issue on unverified versions, keeps hand-built fixtures cited to the Hub tag, and defines a process for re-verifying against new Hub tags.

## Knowledge capture

- Candidate lesson: in GRIT MQTT, a topic's direction (Hub to device command vs device to Hub report) is defined by the Hub's topic mapping and subscription list, not by the topic name. Any consumer must treat `gl`, `s` and `mv` as commands.
- Candidate lesson: `grit/{hub}/mesh/{xtndr}/{to|from}` carries plain-text mesh frames by design. Any `grit/#` subscriber must topic-gate before JSON parsing.
- Candidate lesson: a shared, documented default MQTT password on every Hub is a fleet-wide privacy leak once any client publishes it. A read-only ACL does not make a fleet-default credential acceptable.
